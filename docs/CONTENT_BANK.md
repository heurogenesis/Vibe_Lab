새 문제 은행 테이블은 두 번째 명령에서 생성됩니다. `npm run db:migrate`만으로는 문제 은행이 채워지지 않습니다. 스크립트는 한 트랜잭션에서 초기화하고 같은 버전이 존재하면 덮어쓰지 않습니다. 기존 사용자·과제 테이블을 수정하거나 삭제하지 않습니다. 내용 개정은 새 버전으로 배포해야 합니다.

앱 계정에 DDL 권한이 없다면 마이그레이션 담당 계정으로 실행하고 앱 계정에는 문제 은행 조회 권한을 부여합니다. RDS에서 실행할 때는 CA 검증을 사용하는 접속 설정이 필요합니다.

새 과제 생성 API는 PostgreSQL 모드에서 `learning_question_templates`를 읽어 규칙 기반 문제를 만듭니다. 미초기화 DB에서는 먼저 위 명령이 필요합니다. 파일 체험 모드는 코드에 포함된 동일 템플릿으로 동작합니다. `learning_example_bank`는 API 확장·자료 조회용 저장본이며, 현재 브라우저 실행기는 계속 버전이 고정된 코드 카탈로그를 사용합니다. DB의 빈칸 코드를 임의로 바꿔도 브라우저 실행 코드가 자동 교체되지는 않습니다.

실행기의 NaN/Infinity 경계 테스트는 JSON으로 저장하면 의미가 손실될 수 있어 코드 카탈로그에 유지했습니다. DB의 합성 문제 입력값은 유한한 숫자와 null만 사용합니다.

## 추후 API에서 값 조정하기

서버 내부의 `renderQuestion(template, discipline, parameters, rotation, exerciseId)`를 사용합니다. `parametersSchema`는 허용된 값만 검사하고 정답은 서버의 허용된 계산기로 다시 계산합니다. 임의 JavaScript, SQL, 수식 실행 문자열을 전달하는 구조가 아닙니다.

```typescript
const parameters = {
  lower: 0, upper: 10,
  values: [2, null, 4, 20],
  groups: ['A', 'A', 'B', 'B'],
  outcomes: ['success', 'empty', 'failed', 'failed'],
};
// clean:mean → 유효 평균 3
// quality:rate → 충족 2 / 관측 3 = 0.6667
// trend:moving → 마지막 3개 행의 유효 평균 12
// median:median → 중앙값 4
```

`values`/`groups`는 같은 길이의 1~12개 항목, 상한은 하한보다 커야 하고 숫자는 유한한 -1,000,000~1,000,000 범위입니다. 이 범위는 입력 크기·계산 안정성을 위한 제한이며 전공 확장을 막는 DB enum은 아닙니다. 새로운 물리량이나 알고리즘이 필요하면 서버 검증·템플릿 버전·참조 테스트를 함께 확장합니다.

이후 HTTP 출제 API를 만들 때는 다음 순서를 지킵니다.

1. 사용자 권한과 실습 ID/버전 확인.
2. DB 템플릿 조회 → API/LLM이 제안한 값의 스키마·실습 계약 검사.
3. 서버 계산기로 정답·선택지·해설 재계산. 기준 범위를 바꾸면 예제 설명과 문제 범위도 함께 갱신.
4. 최종 문제 스냅샷을 DB에 저장한 뒤 질문·선택지만 반환.
5. 채점은 저장된 정답 사용. 제출 시 재생성하지 않음.

현재 공개 API는 정답·해설·생성 매개변수를 채점 전에 전달하지 않습니다. 문제 은행 편집/값 조정용 공개 HTTP API는 아직 추가하지 않았습니다. 이번 생성·검증·저장은 LLM API를 호출하지 않습니다.

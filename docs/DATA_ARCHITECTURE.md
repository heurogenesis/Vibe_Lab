# 데이터 아키텍처 재분석 — 무엇을 저장하고 무엇을 저장하지 않는가

- 작성: 2026-09-12 / Claude Code
- 질문: (1) 미구현 항목은 로컬이라서 못 만드는 것인가 (2) 데이터·API 연동에 AWS가 필요한가 (3) DB 볼륨을 줄이려는 설계가 맞는가, 필요한 데이터의 양과 범위는 얼마인가
- 근거: `.data/learning.backup-*.json` 실측, `shared/catalog.ts` 런타임 집계, `server/store.ts`·`shared/data-sources.ts` 코드 확인

## 0. 결론 먼저

1. **미구현 항목 중 로컬이라서 못 만드는 것은 사실상 없습니다.** 막고 있는 것은 인프라가 아니라 **API 키 미발급과 시간**입니다. 유일한 예외는 비밀번호 재설정(메일 발송 수단 필요)과 AWS 배포 자체(CLOUD-01~04)입니다.
2. **데이터·API 연동에 AWS는 필요 없습니다.** 로컬 Node에서 나가는 HTTPS 호출과 EC2에서 나가는 HTTPS 호출은 동일합니다. AWS가 주는 것은 *남이 접속할 수 있다*는 것이지 *더 좋은 데이터*가 아닙니다.
3. **DB 볼륨을 줄이려는 방향은 옳았고, 이미 성공했습니다.** 다만 실측해 보니 **진짜 병목은 저장 용량이 아니라 API 호출 예산**입니다. 그래서 이 문서의 설계는 "덜 저장하기"가 아니라 **"공유 가능한 것을 공유해서 API 호출을 줄이기"**로 목표를 바꿉니다.
4. 실측상 과제 1건 9KB 중 **96~98%가 개인 것이 아니라 프로필로 결정되는 내용**입니다. 이것을 사용자마다 복사해 두는 현재 구조가 유일한 낭비 지점입니다.

## 1. 질문 1 — 로컬이라 못 만드는 항목이 있는가

| 미구현 항목 | 로컬에서 가능한가 | 실제 제약 |
|---|---|---|
| PZ-01~06 (Brave Search + 생성형 AI 개인화) | **가능** | Brave·LLM API 키 미발급. 인프라 무관 |
| P1-02 LLM 피드백 | **가능** | LLM 키 미설정(`ai:false`). 코드 경로는 이미 있음 |
| P1-03 전공별 데이터 확대 | **가능** | 사람이 출처·라이선스·필드를 검수하는 시간. 저장은 애초에 안 함 |
| P1-01 코드 임시 저장 | **가능** | 순수 프런트엔드 작업 |
| DOC-01 문서 갱신 / DEMO-01 포트폴리오 | **가능** | 시간만 필요 |
| 세션 영속화 (재시작 시 로그아웃) | **가능** | 파일 기반 또는 Postgres 세션 저장소로 교체하면 됨 |
| 비밀번호 재설정 | **부분** | 메일 발송 수단이 필요(SES가 아니어도 됨). 외부 서비스 의존이지 AWS 의존은 아님 |
| CLOUD-01~04 | 불가 | 정의상 AWS |

즉 **"로컬이라서 막혔다"는 항목은 사실상 없습니다.** 개인화 기능이 비어 있는 이유는 환경이 아니라, 키가 없고 `usesPractice()` 게이트가 AI 경로를 건너뛰도록 설계돼 있기 때문입니다.

## 2. 질문 2 — AWS로 확장해야 원활히 동작하는가

**AWS가 실제로 주는 것**
- 남(심사위원, 포트폴리오 열람자)이 URL로 접속할 수 있음 ← 유일하게 본질적인 이유
- HTTPS와 `cookie.secure=true`, 실제 CSRF 방어 구성
- 상시 가동, 영속 세션 저장소, API 키를 개인 노트북 밖에 보관

**AWS가 주지 않는 것**
- 더 많은 데이터, 더 나은 검색 결과, 더 나은 개인화 품질 — 전부 API와 프롬프트의 문제
- 응답 속도 — 오히려 외부 API 지연이 지배적이라 차이가 거의 없음

**오히려 주의할 점:** 공개하면 **누구나 우리 API 키로 비용을 쓰게 됩니다.** 로컬에서는 존재하지 않던 위험입니다. 그래서 아래 캐시 설계와 사용자별 호출 쿼터는 원격 공개의 *결과*가 아니라 **전제 조건**입니다.

**9월 22일 포트폴리오 기준 권고:** 기능은 로컬에서 완성하고, 배포는 "데모 영상 + 구조도 + 알려진 한계"로 대체해도 충분합니다. 심사가 실제 접속을 요구할 때만 CLOUD 트랙을 켭니다.

## 3. 실측 데이터 (설계의 근거)

`.data`의 실제 백업 파일을 측정한 결과입니다.

| 항목 | 실측값 |
|---|---|
| 과제 1건 전체 | 8,044 ~ 10,029 bytes |
| └ 커리큘럼 본문 (제목·요약·5단계 레슨·이론·프롬프트·실험·퀴즈) | 7,556 ~ 9,615 bytes (**96~98%**) |
| └ 개인 상태 (진도·퀴즈 결과·제출물·실습 시도) | 122 ~ 252 bytes (**2~4%**) |
| 프로필 1건 | 227 ~ 405 bytes |
| 대화 메시지 1건 | 평균 428 bytes |
| 실습 카탈로그 | 44개 (10개 분야 × 4개 테마 + 프로젝트), **코드 상수라 DB 0** |
| 외부 데이터셋 | 1종, **버전 고정 URL로 실행 시 조회, DB 0** |

**핵심:** 과제의 96~98%는 "이 사람의 것"이 아니라 "이 프로필 조합의 것"입니다. 같은 전공·직무·수준·도메인이면 사실상 같은 내용이 생성되는데, 지금은 사용자마다 9KB씩 복사해 저장합니다.

## 4. 데이터 4계층 설계

| 계층 | 내용 | 저장 위치 | 사용자 증가 시 |
|---|---|---|---|
| **L0 내장** | 실습 카탈로그 44종, 분야·테마·페르소나 정의, 데이터 소스 레지스트리 | 코드 (DB 0) | 증가 없음 |
| **L1 실행 시 조회, 저장 안 함** | 실습용 원본 데이터셋, GitHub 저장소 탐색 결과 | 저장 안 함 (브라우저 캐시) | 증가 없음 |
| **L2 공유 캐시** | 시그니처별 생성 커리큘럼, 검색 질의별 요약 결과 | DB (상한 있음) | **거의 증가 없음** |
| **L3 개인 상태** | 계정·프로필·진도·퀴즈·실습 기록·대화 | DB (필수) | 선형 증가 |

L0과 L1은 이미 이렇게 구현돼 있습니다(**원자료를 긁어와 DB에 넣지 않는다**는 원래 의도가 이미 지켜지고 있습니다). 바꿔야 할 것은 **지금 L3에 섞여 있는 커리큘럼 본문을 L2로 옮기는 것** 하나입니다.

## 5. 공유 캐시 키 설계

### 정규화 시그니처

자유 입력(전공 문자열, 목표 문장)을 그대로 키에 넣으면 캐시가 절대 맞지 않습니다. **유한한 차원으로 정규화한 뒤 키를 만듭니다.**

```
signature = disciplineId : theme : level : domain [: personaId]
```

| 차원 | 값의 수 | 근거 |
|---|---|---|
| disciplineId | 11 (10 + project) | `shared/catalog.ts` |
| theme | 4 | clean / compare / quality / async |
| level | 3 | beginner / intermediate / advanced |
| domain | 3 | business / data / education |
| personaId | 3 (student / engineer / 없음) | 선택적으로 키에 포함 |

- personaId 제외: **396개 조합**
- personaId 포함: **1,188개 조합**

`style`(hands-on / concept-first / guided)은 **키에 넣지 않습니다.** 현재 코드에서 style은 이론 설명의 노출 순서만 바꾸는 렌더링 관심사이므로(`Workspace.tsx`), 같은 생성물을 화면에서 다르게 배치하면 충분합니다. 키에 넣으면 캐시가 3배로 쪼개지고 API 호출도 3배가 됩니다.

### 개인정보 경계 (중요)

프로필의 `goal`(자유 서술)과 `name`, `major` 원문은 **공유 캐시에 절대 들어가면 안 됩니다.** 한 사람이 쓴 목표 문장이 다른 사람 화면에 나타나는 사고로 직결됩니다.

```
공유 계층:  시그니처 → 커리큘럼 골격 (분야·주제·난이도에만 의존)
개인 계층:  goal·이름을 렌더링 시점에 덧입히기 (또는 1~2문장짜리 짧은 개인화 호출만 별도)
```

이 분리는 비용 측면에서도 유리합니다. 큰 생성(레슨 5단계 + 퀴즈)은 캐시로 재사용하고, 개인화는 짧은 호출로 끝냅니다.

## 6. 용량 산정

개인 계층(L3) 사용자 1인 기준, 과제 5건·실습 기록 20건·대화 50건을 가정:

| 항목 | 현재 구조 | 제안 구조 (본문을 L2로) |
|---|---|---|
| 계정 + 프로필 | 0.6 KB | 0.6 KB |
| 과제 5건 | **45 KB** | **1.3 KB** (껍데기 250B × 5) |
| 실습 기록 20건 | 3 KB | 3 KB |
| 대화 50건 | 21 KB | 21 KB |
| **1인 합계** | **약 70 KB** | **약 26 KB** |

| 규모 | 개인 계층 | 공유 계층 | 합계 |
|---|---|---|---|
| 100명 | 2.6 MB | 실사용 조합 100개 × 9KB ≈ 0.9 MB + 검색 캐시 1 MB | **약 5 MB** |
| 1,000명 | 26 MB | 동일 (상한 고정) | **약 30 MB** |
| 전체 조합 소진 (1,188개) | — | 최대 11 MB | — |

**결론: 어떤 시나리오에서도 100MB를 넘지 않습니다.** RDS 최소 인스턴스는 물론이고 지금의 JSON 파일 저장소도 용량으로는 감당합니다(동시성은 별개).

### 단, 상한 하나는 조정 권장

대화 이력이 현재 **500건 상한**(`server/app.ts`)입니다. 평균 428B이므로 최악의 경우 1인 214KB로, **나머지 전부를 합친 것보다 큽니다.** 100건으로 낮추면 1인 43KB로 떨어지고 학습 경험에는 거의 영향이 없습니다.

## 7. 필요한 데이터의 양과 범위

"얼마나 많은 데이터를 모아야 하는가"에 대한 답은 **거의 모을 필요가 없다**입니다. 필요한 것은 데이터 자체가 아니라 **레지스트리(메타데이터)** 입니다.

| 필요한 것 | 지금 | 목표 | 저장 방식 |
|---|---|---|---|
| 실습용 원본 데이터셋 | 1종 | **분야당 1종 = 10종** | 레지스트리에 URL·라이선스·필드만. 원본은 실행 시 조회 (DB 0) |
| 오픈소스 코드 예제 | GitHub 탐색만 분리 존재 | 커리큘럼에 예제 1~2개 연결 | GitHub API 실행 시 조회 + 캐시 (DB 0) |
| 검색 자료 (Brave) | 없음 | 시그니처당 2~3질의 | 제목·URL·스니펫만 캐시 (원문 저장 금지, ~1KB/질의) |
| 생성 커리큘럼 | 44개 고정 카탈로그 | 시그니처별 생성 | L2 공유 캐시 (~9KB/건) |

10종 데이터셋 확보는 **인프라 문제가 아니라 사람이 검수하는 작업**입니다(출처·라이선스·필드 의미·크기). 1종당 30~60분, 총 5~10시간 수준으로 보면 됩니다.

## 8. 진짜 병목 — API 호출 예산

저장이 아니라 호출이 비용입니다. 그런데 캐시를 넣으면 이것도 작아집니다.

| 시나리오 | Brave 질의 | LLM 호출 | 예상 비용 |
|---|---|---|---|
| 캐시 없음, 사용자 1,000명이 각 1회 | 3,000 | 1,000 | Brave $10~15 + LLM $1~5 |
| **시그니처 캐시 적용, 전체 396조합 선행 생성** | 1,188 (월 1,000건 무료 초과분만 과금) | 396 | **Brave ~$1 + LLM $0.5~2** |

**전체 조합을 미리 다 만들어 두어도 몇 달러입니다.** 이건 포트폴리오에서 설명하기 좋은 지점이기도 합니다 — "사용자가 늘어도 생성 비용이 선형으로 늘지 않는 구조".

## 9. 실패·폴백 계층 (원격 공개 전 필수)

외부 API 의존을 늘리는 만큼, 실패해도 학습이 멈추지 않아야 합니다.

```
1순위  L2 공유 캐시 적중        → 즉시 응답, 호출 0
2순위  Brave + LLM 생성          → 성공 시 캐시에 적재
3순위  LLM만 (검색 실패 시)      → 출처 없이 생성, 화면에 명시
4순위  기존 44개 규칙 카탈로그   → 지금의 동작. 항상 성공
```

4순위가 이미 완성되어 있다는 것이 이 프로젝트의 강점입니다. 개인화는 **대체가 아니라 상위 계층 추가**로 설계하고, `usesPractice()` 게이트는 "AI를 막는 문"이 아니라 "폴백 기준"으로 의미를 바꿉니다.

## 10. 사용자 결정이 필요한 사항

1. **Brave Search 계정·키 발급** — 이것이 PZ 트랙의 실제 시작 조건입니다(월 1,000건 무료).
2. **LLM 공급자·모델 확정** — `AGENTS.md`의 기존 미확정 항목. 비용 추정치가 여기에 달려 있습니다.
3. **대화 이력 상한 500 → 100 조정 여부** (개인 데이터의 80%를 차지).
4. **과제 본문을 공유 캐시로 분리하는 리팩터링을 22일 전에 할지, 이후로 미룰지** — 지금 구조로도 동작은 하며, 용량 문제는 1,000명 규모까지 생기지 않습니다. 포트폴리오 설명용 설계도로만 제시하고 구현은 이후로 미루는 선택도 합리적입니다.
